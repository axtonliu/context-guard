# Work Log Share

让未来的自己或接手的 AI 知道：做了什么，为什么这样做，哪些判断已经试错，以及从哪里继续。输出是普通 Markdown 文件，不需要特定笔记软件或外部服务。

## 选择输出

- **完整日志（默认）**：保存本次工作的关键过程、判断和证据。按工作实际复杂度组织篇幅；一次机械操作可以很短，多轮设计或研究应展开会影响理解的细节。
- **交接模式**：用户说“交接”“生成 compact”或要在新会话继续时，在日志末尾增加可直接复制的“恢复会话”段落。时间或上下文紧张时先写恢复段和关键判断，再补仍可可靠还原的过程。不声称知道上下文剩余比例，不自行执行清理、压缩或关闭会话。

沿用用户指定的语言、格式、保存位置。没有指定时，使用本次实际工作项目已有的日志目录；没有约定则保存为该项目下的 `logs/YYYY-MM-DD 主题 工作日志.md`。纯讨论可用当前明确的工作目录。日期取本机当前日期，另有会话日期时注明区别。主题来自内容，不拿安装目录当日志项目。

请求写日志就是对这份本地文件的写入授权。能从上下文推断的项目和路径直接采用并在完成时告知；只有歧义会实质改变归属或覆盖对象才提问。文件同名且无法确认是本次日志时保留已有文件，给新文件加简短后缀。

## 还原事实与判断

从当前会话及其明确关联的产物提取材料。先用已有证据；需要补缺口时只读与这段工作相关的文件或明确绑定的会话记录。

记录以下信息，以方便未来读者理解的顺序组织，不必照搬标题或把每项都写成固定栏目：

- **目标与结果**：用户真正要完成什么、目前做到了哪里。关键措辞会改变任务含义时保留短原句并注明说话者。
- **决策与原因**：遇到的选择、最终取舍及依据。用户拍板、AI 建议、尚未确认的设想要能区分。
- **故意不做**：那些看上去像遗漏、实际出于明确理由而没有做的事。写清理由，避免下一次被“补齐”。
- **被推翻或纠正的判断**：原来怎么想，什么证据或反馈改变了它，现在采用什么做法。没有发生就省略，不制造转折故事。
- **产物与验证**：给出可打开的文件路径；代码任务可附相关 commit、必要的片段或复核命令。说明实测、用户报告、他人报告、推断各自的来源。未运行的验证只能写“待验证”；命令退出成功也只支持它实际检查的范围。
- **未完成与下一步**：把已经完成的工作、尚未验证的结果、实际阻塞分开。写下一步如何推进、需要根据什么证据做哪个判断；不要只写“继续优化”。

材料没有提到的细节不能补成事实。若原始上下文已经缺失，说明缺失范围并保留可靠的部分，不用流畅叙事掩盖空白。Session ID、标题和时间等元数据只在有本会话可靠来源时记录；缺少则省略或写未知。**不能用“最近修改的会话文件”认领当前会话，也不能借用其他会话的 ID 或结论。**

正常调用并不代表项目已完成。若使用状态字段，应按实际工作状态填写。沿用目标目录现有的轻量元数据习惯；没有既有需求就不强制 frontmatter。工作日志不是第二套任务数据库。

## 写下可恢复的交接

交接模式的“恢复会话”要**保存在日志文件中**，不能只发在聊天里。让新会话仅凭这段内容就能找到证据并接着做：

- 当前目标与已经确定的边界。
- 完整日志位置及继续工作真正需要读取的少量文件。
- 已完成的关键结果、当前停在哪一步、尚未解决的问题。
- 下一步动作和判断依据，尤其是分岔口、已踩过的坑、不能重做的失败尝试。
- 延续工作需要遵守的约束及尚需用户决定的事项。

用自然语言写成可直接粘贴的启动指令。依据恢复需要决定长度，不为了短而删掉关键判断。保存后在回复中给出同一恢复段，或在它较长时给出文件链接与明确位置。

## 保存与收尾

只完成本次请求对应的日志文件；额外的记忆更新、任务系统写回、SOP 修改、Git commit、发布或外发，均不由这个 skill 自动触发。日志包含可复用方法时可以在正文留一段，是否迁入其他系统由另一个明确请求决定。

写入后读回本次文件，确认保存位置、关键判断、事实与待办没有混淆；交接模式确认恢复段确实落盘。这里是在验证日志，不是重新运行项目的全部测试。最后报告文件链接、实际工作状态和重要缺口。若宿主没有文件写入能力，直接交付 Markdown 正文并说明尚未保存。
